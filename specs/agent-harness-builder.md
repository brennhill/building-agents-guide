# Feature: Agent Harness Builder — Agent-Type-Agnostic Safety Infrastructure

> Generated by `/feature` on 2026-03-27. Review before implementation.

---

## Intent

### 1. What problem does this solve?

People want to run AI agents autonomously on their codebase or data — background tasks, triggered runs, batch operations — and there's no guided path to set up the safety infrastructure (sandbox, permissions, observability, kill switch, human review gate). The success stories (Spotify, Stripe, OpenAI) describe what they built but not how to replicate it. Current agent frameworks default to everything-on; this provides a default-off, opt-in-capabilities approach.

The scope is any autonomous agent, not just coding agents. Data pipelines, report generators, customer support, monitoring — the harness pattern is the same. The review gate and output validation vary by agent type.

### 2. How will we know it worked?

Pre-flight test suite passes: 36 automated tests + 3 manual red team exercises, all pass before the first autonomous run. Binary: harness verified or not.

Two personas served:
- **Consumer:** ran the setup script (future), has a working locked-down agent in under an hour
- **Professional:** read the guide + attack index, customized the harness for their risk level

### 3. What is out of scope?

- Not every edge case — secure by default, not bulletproof against nation-state attackers
- Multi-agent orchestration — v2
- Agent prompting / CLAUDE.md best practices — v2
- Reference implementation ("the Librarian") — separate repo, used as example in the flavor guide
- Setup script — separate project, requirements captured in `setup-script-requirements.md`
- Framework for every possible agent type — two flavors (code + librarian) demonstrate the pattern, readers generalize
- Windows support — Linux/Mac for v1

### 4. What must NOT happen?

**Guide must not recommend a sandbox config with known gaps.** Every config we publish must be tested against the checklist's own pre-flight suite. Tested or not published.

**Guide must not imply the harness is sufficient for any risk level.** Clear disclaimer: "Whether this pattern is sufficient for YOUR use case depends on your risk level. A report summarizer and a payment processor have different blast radii."

**Standard disclaimer:** This is guidance, not a warranty. Test your own setup. Assess your own risk.

### 5. Pre-mortem findings

1. **Flavors don't scale.** Core sections too tied to two examples. Mitigation: core is truly agent-agnostic, flavors are just "last mile" adaptation (review gate + output validation). Third flavor is obvious by analogy.
2. **Guide gets outdated.** Docker flags change, Anthropic updates recommendations. Mitigation: keep updated, potentially with an agent monitoring the sources (future).
3. **Discovery / competition.** NVIDIA ships a turnkey option. Market risk, can't design against.

### Thinking Record: Intent

**Decided:** Agent-type-agnostic harness guide with two flavor examples (coding + librarian). Default-off capability model. Setup script requirements captured but separate project.
**Reasoning:** People need agents for more than code. The harness pattern is universal; the review gate varies. The Librarian exercises every harness layer and is a real use case.
**Considered and rejected:** Code-only scope (people don't need coding agents, just use Claude interactively). Practice guide (killed, toolkit replaces). Custom measurement scripts (killed, point to DORA tools). Covering every agent type (two flavors, readers generalize). Setup script in this scope (too large).
**Assumptions:** Default-off prevents "uncomment everything" via dangerous-combo warnings + count threshold.
**Risks accepted:** Flavors may not scale. Guide gets outdated. Windows not supported.

## Behavioral Spec

### User Stories

**Current experience:** Find agent framework → install → give it your API key → point at your stuff → hope it's fine → no sandbox, no permissions, no audit trail → works until it doesn't → no idea what happened or how to undo it.

**Desired experience (consumer):** Run setup script → get locked-down agent that can do nothing → edit config to enable capabilities one at a time → dangerous combos trigger warnings → launcher runs pre-flight every time → first run monitored → working agent with full safety infrastructure.

**Desired experience (professional):** Read attack index → understand every risk → follow harness guide → customize for their risk level → choose flavor for their agent type → run pre-flight → deploy with confidence and evidence.

### Mechanism

Default-off capability model. Agent starts locked down (read workspace, write output, nothing else). User opts in to capabilities via config file. Dangerous combinations trigger explicit warnings:

1. Write access (outside container) + no human review
2. Network access + access to credentials
3. Network access + write to external systems
4. No audit logging + any write capability
5. No kill switch + long-running tasks
6. Any 5+ capabilities enabled (slow down)

Launcher always runs pre-flight. Config changes invalidate previous verification. Cannot bypass without building a custom launcher — a conscious choice.

### States and Transitions

| State | Description |
|-------|-------------|
| **Not installed** | No Docker, no config, nothing |
| **Prerequisites** | Docker running, directory structure created |
| **Locked down** | Default config generated, agent can read workspace and write output only |
| **Configured** | User has opted into specific capabilities |
| **Verified** | Pre-flight tests passed for current configuration |
| **Running** | Agent executing tasks |
| **Stopped** | Kill switch, timeout, or task completion — container destroyed |

- Not installed → Prerequisites: setup script (future) or manual install
- Prerequisites → Locked down: config generation
- Locked down → Configured: user edits config, enables capabilities
- Configured → Verified: launcher runs pre-flight (automatic, every launch)
- Verified → Running: agent starts in container
- Running → Stopped: kill/timeout/completion, container destroyed
- Configured → Configured: user changes capabilities (warns on dangerous combos)
- Config change invalidates Verified — next launch re-runs pre-flight

### Error Cases

- **Setup failures:** Detect and clear error. Don't silently proceed without Docker.
- **Config validation:** Invalid format → clear error. V2: "test your config" verifies each capability.
- **"Uncomment everything" problem:** Dangerous combo warnings at 5 specific lethal combos + count threshold at 5.
- **Config change without re-verification:** Launcher always runs pre-flight. No bypass without custom launcher.
- **Runtime failures (v2):** Timeout mid-task, disk full, API key expiry — graceful handling is future work.
- **Linux/Mac only for v1.** Windows errors clearly.

### Thinking Record: Behavioral Spec

**Decided:** Two personas, same harness. Default-off with opt-in capabilities. Dangerous combo warnings. Launcher always pre-flights.
**Reasoning:** Opposite of every current framework (default everything on). Speed bumps work. Consumer gets sane defaults, professional customizes.
**Assumptions challenged:** "Users will start restricted" → challenged with "uncomment everything." Mitigated by combo warnings + count threshold. "Pre-flight runs once" → challenged. Mitigated by launcher always running it.
**Risks accepted:** Windows not v1. Runtime graceful handling not v1. Someone can build custom launcher to bypass.

## Design Approach

### Conceptual approach

Option B: Split into layers. Agent-agnostic core guide + separate flavor files. New flavors added as separate files without touching the core.

Core sections (universal): sandbox, credentials, observability, kill switch, resource limits, pre-flight.

Flavor sections (vary by type): review gate mechanism, output validation, allowed network destinations, example configs.

### Codebase context

Current guide is 515 lines, ~30 code-specific references in 5 of 10 steps. Core sections (Steps 1-2, 5, 8-9) are already agent-agnostic. Steps 3, 4, 6, 7, 10 need genericizing with code-specific content extracted to `flavors/coding-agent.md`.

### Thinking Record: Design Approach

**Decided:** Split into layers (Option B) over refactor-in-place (Option A).
**Reasoning:** New flavors don't touch core guide. Scales to contributions.
**Alternatives rejected:** Refactor in place — every new flavor edits the main doc.
**Codebase findings:** Refactor is surgical — 5 of 10 steps need work, rest is already generic.

## Implementation Design

### Architecture

```
building-agents-guide/
├── README.md                              # Two paths: consumer (setup script) / professional (guide)
├── how-to-use-the-checklist.md            # Refactored: agent-type-agnostic
├── how-to-build-an-agent-harness.md       # Refactored: agent-agnostic core only
├── attack-risk-index.md                   # Light refactor: add non-code examples
├── flavors/
│   ├── README.md                          # What flavors are, how to pick yours
│   ├── coding-agent.md                    # Last mile: PRs, CI gates, branch protection, secret detection
│   └── librarian-agent.md                 # Last mile: network allowlist, citation validation, source triage
└── setup-script-requirements.md           # Detailed spec for future setup script project
```

### What changes where

**`how-to-build-an-agent-harness.md`:**
- Steps 1, 2, 5, 8, 9: keep as-is (already agnostic)
- Step 3 (credentials): genericize "push branches" → "interact with external systems." Code specifics → flavor file.
- Step 4 (boundaries): genericize tool allowlist examples. Code specifics → flavor file.
- Step 6 (gates): rename from "CI Gates" → "Output Gates." Generic pattern: "agent output passes through automated checks before human review." Code-specific checks → flavor file.
- Step 7 (human review): genericize from "PR review" → "review gate." Pattern: agent produces artifact, human reviews before it has effect. Code: PR. Librarian: source approval queue + summary spot-check.
- Step 10 (first run): genericize "review the first PR" → "review the first output."
- Each genericized step links: "See your [flavor guide](flavors/) for specifics."

**`flavors/coding-agent.md`:** (~150 lines)
- Credentials: git tokens, scoped to create-branch + create-PR
- Boundaries: tool allowlist (git, npm/pip/go, test runner). Protected paths (.github/workflows, .env).
- Output gates: CI pipeline, secret detection in diff, dependency audit
- Review gate: PR-based. Branch protection. Reviewer sees task + diff + audit trail.
- First run: pick Tier 1 service, review first PR carefully

**`flavors/librarian-agent.md`:** (~150 lines)
- Credentials: API keys for LLM provider (via proxy). No git credentials needed unless writing to a repo.
- Boundaries: network allowlist (arxiv.org, scholar.google.com, configured RSS feeds). Read from web, write only to codex output directory.
- Output gates: citation validation (URLs resolve, authors exist), no hallucinated papers, summary matches source, no embedded prompt injection in output
- Review gate: new sources flagged for human approval before added to regular sweep. Summaries spot-checked (sample 10-20% for accuracy).
- First run: give it 3-5 known papers, verify summaries are accurate before letting it discover sources.
- Failure modes: hallucinated citations, source drift (blog turns to spam), summary bias, unbounded source discovery

**`attack-risk-index.md`:** Light touch — add a Librarian example alongside code examples in 3-4 entries (output exfiltration, indirect prompt injection, memory poisoning, denial-of-wallet).

**`how-to-use-the-checklist.md`:** Replace "pick a repo" with "pick a workspace/task." Replace "CI" with "output gates."

**`setup-script-requirements.md`:** (~200 lines) Detailed spec for the future consumer-path project:

Prerequisites to handle:
- Detect OS (Linux/Mac, error on Windows)
- Install Docker if missing
- Check for git
- Prompt for LLM API key, validate it works

What the script creates:
- Directory structure (workspace, output, audit-logs, rollback)
- Locked-down Docker config
- Capability config file (everything commented out / default off)
- Kill script
- Pre-flight test runner
- .gitignore

Capability config format (YAML):
- network (enabled, allowlist)
- write_external (enabled, paths)
- secrets (method, path)
- human_review (enabled, method)
- tools (allowlist)
- resource_limits (memory, cpus, disk, timeout, max_iterations, pids_limit)
- audit (enabled, destination, retention_days)

Dangerous combination warnings (5 specific + count threshold):
1. write_external + !human_review
2. network + secrets != none
3. network + write_external
4. !audit + write_external
5. !kill_switch + timeout > 60min
6. 5+ capabilities enabled

Launcher behavior:
1. Parse config, check combos, prompt if dangerous
2. Run pre-flight against current config
3. Fail → stop, show which test
4. Pass → launch in container, stream audit
5. On exit → destroy container, preserve logs + output

Gate installation:
- Detect language from workspace
- Offer Tier 0 gates from toolkit quick-starts
- Unknown language → web search, warn user

### Structural issues flagged

- The current harness guide mixes universal and code-specific content in the same steps. The refactor must cleanly separate them or readers of non-code flavors will be confused by leftover code references.
- The attack-risk-index is heavily code-centric. A full rewrite to be agent-agnostic is out of scope — light-touch additions of non-code examples are sufficient for v1.

### Constraints and Non-negotiables

- **Security:** Every config we publish must pass the checklist's own pre-flight suite. Tested or not published.
- **Reliability:** Launcher always runs pre-flight. No bypass without custom code.
- **Honesty:** "Whether this pattern is sufficient for YOUR use case depends on your risk level."

### Known AI Blind Spots

- [x] Edge cases: Flavors that don't fit the core pattern → disclaimer about risk assessment. Librarian with network access → explicit allowlisting guidance.
- [N/A] Concurrency: Guide, not a service.
- [x] Error handling: Config validation for format errors. Runtime graceful handling is v2.
- [x] Security: Librarian needs network access — first flavor where --network none doesn't work. Flavor must be explicit about allowlisting.
- [x] Non-prompted concerns: Librarian output published to web → hallucinated links could be malicious. Flavor flags this.
- [x] Hallucination risk: Librarian's #1 failure mode. Flavor includes validation: verify URLs resolve, authors exist, findings match source.

### Rollback Plan

- **Trigger signal:** Users report guide steered them wrong, config has a gap, flavor is misleading
- **Method:** Git revert on specific file. Flavors are separate files so a bad flavor doesn't affect the core.
